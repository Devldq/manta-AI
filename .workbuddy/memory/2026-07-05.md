## 文档处理状态持久化——刷新页面后可见正在进行的任务

### 问题
文档上传后处理中（parsing→chunking→embedding→storing）的状态仅存在于后端内存中，未持久化到数据库。页面刷新后，前端无法知道有文档正在处理。

### 解决方案
**后端先写入 `processing` 记录，处理完成由 `addDocument` 覆盖为 `ready`，失败更新为 `error`。前端轮询 `processing` 文档直到全部完成。**

### 改动内容

1. **SQLite provider 新增方法**：
   - `insertPendingDocument(kbId, metadata)` — 处理前插入 `status='processing'` 行
   - `updateDocumentStatus(docId, status, error?)` — 更新文档状态（成功→ready 已由 addDocument 处理，失败→error）

2. **后端上传路由**：
   - 在 pipeline 处理前调用 `insertPendingDocument` 写入 processing 记录
   - catch 块中调用 `updateDocumentStatus(docId, 'error', errMsg)` 更新为失败状态
   - `pendingDocId`/`pendingKbId` 提到 try 外确保 catch 可访问

3. **前端 store 轮询**：
   - `checkProcessingDocs(kbId)` — 检查文档列表中是否有 processing/pending 状态的文档，有则启动 3s 轮询
   - `stopDocPolling()` — 清除轮询定时器
   - `fetchDocuments` 完成后自动调用 `checkProcessingDocs`
   - 轮询时 `invalidateCache` 绕过 SWR 30s 缓存
   - 全部处理完成后刷新知识库统计
   - `reset()` 时清理定时器

4. **DocCard UI 增强**：
   - processing 状态：图标改为旋转 Loader，边框高亮，操作按钮始终可见
   - error 状态：图标改为 AlertCircle，显示错误信息文本
   - ready 状态：行为不变

### 修改的文件
- `packages/rag/src/sqlite-vec-provider.ts` — insertPendingDocument + updateDocumentStatus
- `packages/backend/src/routes/rag.ts` — 上传路由先写 processing，catch 写 error
- `packages/frontend/src/stores/rag-detail-store.ts` — checkProcessingDocs/stopDocPolling + fetchDocuments 触发轮询

## 后端重启清理 stuck processing 文档

### 问题
后端重启后，上次处理中断的文档会永远卡在 `processing` 状态。

### 解决方案
后端启动时调用 `cleanupStaleDocuments()`，将所有 `processing` 状态的文档标记为 `error`，错误信息 "处理被中断（服务器重启），请重新上传此文件"。

### 改动
1. **SQLiteVecProvider 新增 `cleanupStaleDocuments()`**：
   - 查询所有 `status='processing'` 的文档
   - 批量更新为 `status='error'`
   - 返回被清理的文档列表（kbId, docId, docName）

2. **server.ts 启动流程**：
   - 在 `start()` 函数中、`app.listen()` 之前调用 `cleanupStaleDocuments()`
   - 用 `try/catch` 包裹，清理失败不影响启动
   - 日志输出被清理的文档列表

### 刷新后状态恢复流程
1. 页面刷新 → `fetchDocuments` 从 DB 拿到 `processing` 文档
2. `checkProcessingDocs` 检测到 → 启动 3s 轮询
3. 后端 pipeline 完成后 `addDocument` 将状态改为 `ready`（INSERT OR REPLACE 覆盖 processing 记录）
4. 前端轮询检测到无 processing → 停止轮询 + 刷新 KB 统计
5. 后端重启场景：stuck processing → `cleanupStaleDocuments` → 标记为 error → 前端轮询检测到非 processing → 停止轮询 + 展示错误

### 修改的文件
- `packages/rag/src/sqlite-vec-provider.ts` — cleanupStaleDocuments 方法
- `packages/backend/src/server.ts` — start() 中调用清理

## 刷新页面后恢复暂存文件队列 + 自动继续处理

### 问题
用户选了 10 个文件，点击执行后 2 个正在处理。刷新页面后：
- 处理中的 2 个文件可见（后端 DB 有 `processing` 记录）
- 等待处理的 8 个文件丢失（仅存在于浏览器内存）
- 用户希望刷新后与刷新前状态一致：看到等待队列 + 处理中文件，并自动继续处理

### 解决方案
**用 IndexedDB 持久化暂存文件队列 + 批处理元数据，刷新后恢复并自动继续处理。**

### 改动

1. **新建 `staged-files-db.ts`（IndexedDB 持久化模块）**：
   - `PersistedStagedFile` — 包含 File 对象（IndexedDB 原生支持存储 File/Blob）
   - `BatchMeta` — 批处理元数据（kbId, processingStarted, totalFiles, concurrency, chunkingConfig）
   - CRUD：`saveStagedFiles`, `loadStagedFiles`, `removeStagedFileById`, `clearAllForKb`
   - Meta：`saveBatchMeta`, `loadBatchMeta`, `clearBatchMeta`
   - 使用 `txDone` 包装 IDBTransaction 完成事件（`tx.done` 在当前 TS DOM 类型版本中不可用）

2. **store 修改（`rag-detail-store.ts`）**：
   - 新增 `currentKbId` 状态字段（`fetchKnowledgeBase` 时设置）
   - `addStagedFiles`/`removeStagedFile`/`clearStagedFiles` — 同步到 IndexedDB（fire-and-forget）
   - `processStagedFiles` — 接受 `options.alreadyCompleted` 参数，开始时保存 `BatchMeta`，结束时清除 IndexedDB
   - 新增 `workersActive` 模块级标记 — 防止 `processStagedFiles` 重入
   - 新增 `restoreBatchSession(kbId)` — 核心恢复方法：
     - 加载 `BatchMeta` + 暂存文件
     - 用 name+size 匹配后端文档，过滤掉 processing/ready/pending 的（已在后端）
     - error 的保留在队列中（可重试）
     - `batchCompletedCount = total - remaining - processing`
     - 有 processing 文档 → 等轮询完成再继续
     - 无 processing 文档 → 立即 `processStagedFiles`
   - `checkProcessingDocs` 轮询增强：
     - 恢复阶段更新 `batchCompletedCount`（`total - staged - processing`）
     - 全部 processing 完成后检查 `batchProcessing && stagedFiles.length > 0` → 自动 `processStagedFiles`
   - 接口新增 `batchCompletedCount`/`batchActiveFiles`（替代旧的 `batchCurrent`/`batchCurrentProgress` 等）

3. **UI 修改（`detail.tsx`）**：
   - `useEffect` 改为 `fetchDocuments(id).then(() => store.restoreBatchSession(id))`
   - 暂存区条件从 `!batchProcessing` 改为始终显示（批处理时只读）
   - `StagedFileItem` 的 `onRemove` 改为可选，批处理时不显示移除按钮
   - `BatchProcessingIndicator` 新增「等待处理: N 个文件」提示
   - 批处理时隐藏 ChunkingConfigPanel 和「处理全部」按钮

### 恢复流程
1. 页面加载 → `fetchDocuments` → `restoreBatchSession`
2. IndexedDB 加载 BatchMeta（processingStarted=true）+ 暂存文件
3. 后端文档匹配 → 过滤掉已处理文件 → 剩余暂存文件恢复到 store
4. 有 processing 文档 → 轮询等待完成
5. processing 全部完成 → 自动 `processStagedFiles(alreadyCompleted=已计数)`
6. Workers 处理剩余文件 → 完成后清除 IndexedDB

## Token 分析实时渲染（流式期间每步完成后即显示）

### 问题
对话界面中 token 分析（TokenBreakdown 组件）只在 Agent Loop 整体结束后才渲染。用户需要每次输出完成（每步 finish）就看到 token 分析。

### 原因
1. **后端**：`stream-transformer.ts` 故意剥离 `finish-step` 和 `finish` chunk 中的 usage 字段（UIMessageChunk schema 严格模式）
2. **后端**：token 数据只在 `onFinish` 回调中持久化（Loop 结束后才写入）
3. **前端**：`MessageRow.tsx` 有 `!isStreaming` 条件，流式期间不渲染 token 区域
4. **前端**：token 数据只在 `status` 从 streaming→ready 时 fetch 获取

### 解决方案
通过自定义 SSE 事件 `manta:step-usage` 在每步完成后立即推送 token 用量，前端用 fetch 拦截器捕获。

### 改动内容

1. **后端 `agent-loop.ts`**：每步 fullStream 消费完成后，发送 `manta:step-usage` SSE 事件（含 stepIndex/usage/toolNames）
2. **前端 `page.tsx`**：
   - 新增 `createStepUsageInterceptor` 函数：自定义 fetch 包装器，用 `TransformStream` 拦截 SSE 原始字节，提取 `manta:step-usage` 事件
   - 新增 `liveStepUsages` 状态：实时收集 step usage 数据
   - `DefaultChatTransport` 传入 `fetch: interceptedFetch`
   - 发送新消息/流结束/重连结束时重置 `liveStepUsages`
   - 传 `liveStepUsages` 给最后一条 streaming 的 MessageRow
3. **前端 `MessageRow.tsx`**：
   - 新增 `liveStepUsages` prop
   - 计算 `effectiveUsage`/`effectiveStepUsages`：优先 metadata（完整数据），回退 live 数据
   - 移除 `!isStreaming` 条件：有 effective data 就渲染 token 分析
   - 流式时 ≥1 步即显示 TokenBreakdown（非流式仍需 >1 步）
   - 添加 `live` 脉冲指示器标记实时数据
4. **前端 `useReconnectSSE.ts`**：
   - 新增 `onStepUsage` 回调参数
   - SSE 解析循环中拦截 `manta:step-usage` 事件并调用回调
   - 使用 ref 存储回调避免 connect 函数重建

### 数据流
```
agent-loop 每步 finish → sendChunk(manta:step-usage)
  → SSE 流 → DefaultChatTransport 的 fetch 拦截器
  → TransformStream 解析 → onStepUsage 回调
  → setLiveStepUsages → MessageRow 重新渲染
  → effectiveUsage/effectiveStepUsages → TokenBreakdown 实时展示
```
